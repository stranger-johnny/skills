# Anthropic のスキル作成ベストプラクティス

このファイルは、Anthropic の「スキル作成のベストプラクティス」を要約したものです。
スキルに何を書き、ファイルをどう分けるかを決めるときに読みます。
書式は [マークダウンスタイル](markdown-style.md) に従います。

## 簡潔に書く

Claude のコンテキストウィンドウには、スキルのほかに、システムプロンプト、
会話履歴、他のスキルの情報も入ります。
スキルの文が長いほど、他の情報に使える量が減ります。

Claude は一般的な知識をすでに持っています。
PDF とは何か、ライブラリとは何かといった説明は書きません。
社内のテーブル名、チーム固有のルール、間違えやすい手順のように、
Claude が知らない情報だけを書きます。

段落を書いたら、次の2点を確かめます。

- Claude はこの説明がなくても作業できるか。
- この段落を削ると、Claude の作業結果は変わるか。

## 自由度を決める

指示をどこまで具体的に書くかは、手順を誤ったときの影響の大きさで決めます。

やり方が複数あり、状況に応じて判断が変わる作業は、方針だけを文で書きます。
コードレビューがこれに当たります。

推奨するやり方はあるものの、多少の違いは許される作業は、擬似コードや
引数付きのスクリプトを示します。
レポートの生成がこれに当たります。

手順を誤るとデータが壊れる作業や、順序が決まっている作業は、実行する
コマンドをそのまま書き、変更しないよう指示します。
データベースのマイグレーションがこれに当たります。

## フロントマター

SKILL.md の先頭には、`name` と `description` を書いた YAML フロントマターを置きます。

`name` には次の制約があります。

- 64文字以内で書く。
- 小文字、数字、ハイフンだけを使う。
- XML タグを含めない。
- `anthropic` と `claude` を含めない。

`description` には次の制約があります。

- 空にしない。
- 1,024文字以内で書く。
- XML タグを含めない。

## 命名

名前には、スキルが行う作業を動名詞形で書くことを第一に考えます。
`processing-pdfs`、`analyzing-spreadsheets`、`writing-documentation` がその例です。
`pdf-processing` のような名詞句や、`process-pdfs` のような動詞の形も使えます。

`helper`、`utils`、`tools`、`documents`、`data` のような名前は避けます。
名前を見ても、スキルが何をするのか分からないからです。

複数のスキルを作る場合は、同じ命名の形に揃えます。
ディレクトリ名と `name` の値も同じにします。

## description の書き方

Claude は、100を超えるスキルの中から、description だけを読んで使うスキルを選びます。
本文は、スキルを使うと決めた後にしか読みません。
そのため、スキルをいつ使うかは、本文ではなく description に書きます。

description は三人称で書きます。
Claude は description をシステムプロンプトの一部として読みます。
「I can」や「You can」で書くと、誰の発言なのかが文ごとに変わってしまいます。

description には、スキルが何をするかと、いつ使うかの両方を書きます。
いつ使うかは「Use when ...」に続けて書き、ユーザーが依頼に使う言葉を並べます。
ファイル形式、ツール名、作業名のように、ユーザーが実際に口にする言葉を入れます。
ユーザーが日本語で依頼するなら、日本語の言葉も入れます。

Claude は、使えるスキルがあっても使わずに済ませることがあります。
関連する依頼で Claude がこのスキルを選ぶよう、使う場面は少し広めに書きます。

```yaml
# 良い例
description: Extracts text and tables from PDF files, fills forms, and merges
  documents. Use when working with PDF files or when the user mentions PDFs,
  forms, or document extraction.

# 悪い例
description: Helps with documents
```

## 段階的開示

Claude は、スキルの中身を3段階に分けて読み込みます。

1.  `name` と `description` は、常にコンテキストに入っています。
1.  SKILL.md の本文は、Claude がスキルを使うと決めたときに読みます。
1.  同梱ファイルは、Claude が必要と判断したときに読みます。
    スクリプトは、中身を読まずに実行できます。

SKILL.md の本文は500行未満にします。
SKILL.md には作業の概要と、詳しい資料の場所を書きます。
ファイルの分け方には、次の3つの型があります。

1つ目は、SKILL.md によく使う手順を書き、詳しい説明を参照ファイルに置く型です。

2つ目は、領域ごとにファイルを分ける型です。
`references/finance.md` と `references/sales.md` のように分けておくと、
Claude は依頼に関係する領域のファイルだけを読みます。

3つ目は、基本の手順を SKILL.md に書き、特殊な場合の手順だけを別ファイルに置く型です。

### 参照は1階層にする

参照ファイルは、すべて SKILL.md から直接リンクします。
参照ファイルから別の参照ファイルにリンクすると、Claude は `head -100` のような
コマンドでファイルの一部だけを読み、残りを読み落とすことがあります。

### 長い参照ファイルには目次を置く

100行を超える参照ファイルには、先頭に目次を置きます。
Claude がファイルの冒頭だけを読んだ場合でも、どんな内容があるかが分かります。

### ファイル名とディレクトリ

- ファイル名には内容を表す言葉を使います。`doc2.md` ではなく `form_validation_rules.md` とします。
- 領域や機能ごとにディレクトリを分けます。
- パスの区切りにはスラッシュを使います。バックスラッシュは Unix で動きません。

## ワークフローとフィードバックループ

### 複雑な作業は手順に分ける

複数の段階がある作業は、順番のある手順に分けます。
手順が多い場合は、Claude が応答にコピーして、終わった項目に印を付けられる
チェックリストを付けます。

````markdown
## フォーム入力のワークフロー

次のチェックリストをコピーして、終わった項目に印を付けてください。

```text
- [ ] Step 1: フォームを分析する
- [ ] Step 2: フィールドの対応表を作る
- [ ] Step 3: 対応表を検証する
- [ ] Step 4: フォームに値を入れる
```

### Step 1: フォームを分析する

`python scripts/analyze_form.py input.pdf` を実行します。
````

### 検証と修正を繰り返す

検証して、誤りを直して、もう一度検証する手順を入れます。
この手順があると、Claude は誤りを次の段階に持ち越しません。
検証には、スクリプトを使っても、スタイルガイドのような文書と照らし合わせてもかまいません。
手順には、検証に通るまで次の段階に進まないことを書きます。

### 条件で手順を分ける

新規作成か既存の編集かのように、条件によって手順が変わる場合は、
それぞれの手順の場所を明記します。
分かれた先の手順が長くなったら、別のファイルに移します。

## 内容の指針

### 日付に依存する記述を避ける

「2025年8月より前なら古い API を使う」のような記述は、時間がたつと誤りになります。
現在の方法を本文に書き、古い方法は `## 古いパターン` という見出しの下に書きます。

### 用語を統一する

1つの概念には、1つの用語を使います。
「フィールド」「ボックス」「要素」が混ざると、Claude はそれぞれを別のものと解釈することがあります。

### テンプレートを示す

出力の形式が決まっている場合は、テンプレートを示します。
形式を変えてはいけない場合は、テンプレートをそのまま使うよう書きます。
内容に合わせて変えてよい場合は、テンプレートを初期の形として使い、必要に応じて変えるよう書きます。

### 例を示す

出力の質が例によって変わる作業には、入力と出力の組を載せます。
文で説明するより、例を見せたほうが、文体や詳しさの程度が正確に伝わります。
例には、実際の作業で出てくる具体的な値を使います。

### 方法を1つに決める

「pypdf か pdfplumber か PyMuPDF を使う」のように選択肢を並べると、Claude は選ぶのに迷います。
通常使う方法を1つ書き、その方法が使えない場合に限って別の方法を書きます。

### 規則には理由を書く

`ALWAYS` や `NEVER` を大文字で書く前に、規則の理由を書けないか考えます。
理由が分かれば、Claude は例にない場面でも正しく判断できます。

## 実行可能なコードを含むスキル

### エラーはスクリプトの中で処理する

スクリプトは、起こりうるエラーを自分で処理します。
ファイルがない場合や権限がない場合は、原因が分かるメッセージを出すか、代わりの動作をします。
エラーの処理を Claude に任せると、Claude は毎回その場で対処を考えることになります。

### 定数には根拠を書く

`TIMEOUT = 47` のような、根拠の分からない値は使いません。
値を決めた理由を、コメントで書きます。
作者が正しい値を知らなければ、Claude にも正しい値は分かりません。

### よく使う処理をスクリプトにする

決まった処理は、Claude に毎回コードを書かせるより、スクリプトにしておくほうが結果が安定します。
コードを生成しない分、トークンと時間も減ります。

指示の中では、スクリプトを実行するのか、読むのかを書き分けます。

- 実行させる場合は「`analyze_form.py` を実行してフィールドを抽出する」と書きます。
- 読ませる場合は「抽出の手順は `analyze_form.py` を参照する」と書きます。

### 変更の計画を先にファイルに書き出す

大量の変更や、元に戻せない操作では、計画、検証、実行の順に進めます。
たとえば、変更の計画を `changes.json` に書き出し、スクリプトで検証してから適用します。
検証スクリプトのエラーメッセージには、見つからなかった項目と、使える項目の一覧を含めます。

### 依存するパッケージを書く

必要なパッケージがインストール済みだとは考えません。
必要なパッケージと、そのインストール方法を SKILL.md に書きます。
実行環境によってはネットワークに接続できず、パッケージをインストールできないこともあります。

### MCP ツールは完全修飾名で書く

MCP ツールは、`BigQuery:bigquery_schema` のように `ServerName:tool_name` の形で書きます。
サーバー名がないと、複数の MCP サーバーがある環境で、Claude がツールを見つけられないことがあります。

## 評価と反復

### 評価を先に作る

長い文書を書く前に、評価を作ります。
評価を先に作ると、実際に起きる問題だけを解決するスキルになります。

1. スキルなしで Claude に代表的な作業をさせ、失敗した点や足りない情報を記録します。
1. その点を確かめるシナリオを3つ作ります。
1. スキルなしでの結果を、比較の基準として記録します。
1. 足りない情報を補うのに必要な分だけ、指示を書きます。
1. 評価を実行し、基準と比べて指示を直します。

### 2つの Claude で反復する

スキルを書く Claude と、スキルを使う Claude を分けて考えます。
使う側の Claude に実際の作業をさせ、うまくいかなかった点を書く側の Claude に伝えて直します。

使う側の Claude の動きを見るときは、次の点を確かめます。

- 予想と違う順序でファイルを読んでいないか。
- 作業に必要な参照ファイルを開かずに作業していないか。
- 同じファイルを何度も読んでいないか。何度も読むなら、その内容を SKILL.md に移します。
- 一度も読まれないファイルがないか。読まれないなら削除するか、SKILL.md での案内を目立たせます。

### 使う予定のモデルすべてで試す

Opus で十分な指示でも、Haiku では情報が足りないことがあります。
Haiku に合わせて詳しく書いた説明は、Opus には不要なことがあります。

## 公開前のチェックリスト

### 内容と構成の確認

- [ ] description に具体的な用語が入っている。
- [ ] description に、何をするかといつ使うかの両方が書いてある。
- [ ] SKILL.md の本文が500行未満である。
- [ ] 詳しい内容を、必要に応じて別のファイルに分けてある。
- [ ] 日付に依存する記述がないか、`## 古いパターン` にまとめてある。
- [ ] 用語が統一されている。
- [ ] 例に具体的な値を使っている。
- [ ] 参照ファイルがすべて SKILL.md から直接リンクされている。
- [ ] ワークフローの手順が順番に並んでいる。

### コードとスクリプトの確認

- [ ] スクリプトがエラーを自分で処理している。
- [ ] すべての定数に、値を決めた理由が書いてある。
- [ ] 必要なパッケージを書き、実行環境で使えることを確かめた。
- [ ] パスがすべてスラッシュで区切られている。
- [ ] 元に戻せない操作の後に、結果を確かめる手順がある。

### テストの確認

- [ ] 評価を3つ以上作った。
- [ ] 使う予定のモデルで試した。
- [ ] 実際の作業で試した。
