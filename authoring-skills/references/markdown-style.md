# スキルのためのマークダウンスタイル

このファイルは、Google Markdown style guide をスキル向けに要約したものです。
規則ごとに、その理由と良い例、悪い例を載せています。
SKILL.md と参照ファイルは、この規則に沿って書きます。
文の組み立てや言葉の選び方は、[文章の書き方](prose-style.md) で扱います。

## 基本方針

マークダウンは、レンダリングされないまま読まれることがよくあります。
Claude もソースをそのまま読みます。
そのため、レンダリング後の見た目より、ソースの読みやすさを優先します。

ドキュメントは少なく、正確に保ちます。
古くなった記述は、残さずに削除します。

完璧な変更でなくても、今より良くなる変更は取り入れます。
Google のガイドは、これを「Better is better than best」と呼んでいます。

## 文書の骨格

ファイルの中身は、次の順に並べます。
この順にすると、読み手は冒頭の数行で、そのファイルを読む必要があるかを判断できます。

1. H1 のタイトルを1つだけ置きます。
1. タイトルの直後に、初めて読む人に向けた1〜3文の導入を書きます。
1. 100行を超えるファイルでは、導入の後に目次を置きます。
1. 残りの見出しは、すべて H2 から始めます。
1. 必要なら、最後に「関連資料」の節を置きます。

````markdown
# PDF フォーム入力

このファイルは、PDF のフォームに値を入れて保存する手順です。

## フィールドを抽出する
...

## 関連資料

- [pypdf のドキュメント](https://pypdf.readthedocs.io/)
````

SKILL.md では、フロントマターの直後に H1 を置きます。
H1 には `name` の値ではなく、人が読むためのスキル名を書きます。

## 行の長さと改行

### 80文字で折り返す

本文は、1行を80文字以内にします。
行が短いと、差分のレビューで変わった箇所を見つけやすくなります。
横にスクロールせずに読めるようにもなります。

次の行は、80文字を超えてもかまいません。

- リンクや URL を含む行
- 表の行
- 見出し
- コードブロックの中の行
- YAML フロントマターの行

### 日本語の改行位置

日本語は、句点「。」か読点「、」の直後で改行します。
多くのレンダラーは、ソースの改行を空白として表示します。
語の途中で改行すると、表示したときに語の間に空白が入ります。
1文を1行に書くと、たいていの行は80文字に収まり、差分も文ごとに分かれます。

```markdown
<!-- 悪い例: 語の途中で改行している -->
スキルの説明文はシステムプロンプトに挿入されるため、三人称
で書きます。

<!-- 良い例: 読点の直後で改行している -->
Claude はスキルの説明文をシステムプロンプトから読むため、
説明文は三人称で書きます。
```

### 行末に空白を残さない

マークダウンでは、行末の2つの空白が改行として扱われます。
この空白はソースでは見えないので、意図しない改行の原因になります。
改行が必要な場合は、段落を分けます。
どうしても段落の中で改行したい場合に限り、行末に `\` を置きます。

## 見出し

### `#` で始める形式を使う

見出しは `#` で始めて書きます。
次の行に `===` や `---` を引いて見出しにする書き方は使いません。
`#` の後には空白を1つ入れ、見出しの前後には空行を入れます。

### 見出しをファイルの中で重複させない

レンダラーは見出しからアンカーを作り、Claude は `grep` で見出しを探します。
同じ名前の見出しが2つあると、リンクや検索がどちらを指すのか分からなくなります。
小見出しにも、親の見出しの語を含めます。

```markdown
<!-- 悪い例 -->
## フォーム入力
### 概要
## 検証
### 概要

<!-- 良い例 -->
## フォーム入力
### フォーム入力の概要
## 検証
### 検証の概要
```

### 見出しの階層を飛ばさない

H2 の次に H4 を置くような書き方はしません。
階層を飛ばすと、目次やアウトラインで見出しの親子関係が崩れます。

### 太字の行ではなく見出しを使う

`**Step 1: 分析する**` のような太字の行は、見出しになりません。
レンダラーはアンカーを作らず、アウトラインにも表示しません。
ワークフローの各ステップは、`### Step 1: フォームを分析する` のように見出しで書きます。

## リスト

### 番号の振り方

長いリストや、後で項目が増えそうなリストは、すべての番号を `1.` にします。
こうすると、項目を足したり並べ替えたりしても、他の行の番号を直す必要がありません。
短く、変わる見込みのないリストは、`1.` `2.` `3.` と順に振ってもかまいません。

### ネストは4スペースで字下げする

ネストしたリストと、リスト項目の2行目以降は、4スペースで字下げします。
2スペースや3スペースの字下げは、レンダラーによって解釈が変わります。

```markdown
1.  Analyze the form.
    The script writes `fields.json`.
1.  Validate the mapping.
    -   Fix every reported error.
    -   Run the validator again.
```

項目が1行で、ネストもないリストでは、マーカーの後の空白は1つでかまいません。
項目が2行以上になる場合やネストする場合は、上の例のように本文を4文字目から始めます。

### マーカーを揃える

1つのファイルの中では、箇条書きのマーカーを `-` か `*` のどちらかに揃えます。
進み具合を記録するチェックリストには `- [ ]` を使います。

### 太字のラベルとコロンを並べない

「**性能**: 性能が向上しました」のように、太字のラベルが直後の文を繰り返すだけのリストは書きません。
ラベルを外して文にするか、小見出しにします。
項目に名前を付けたい場合は、名前の後を句点で区切り、名前とは別の情報を続けます。

```markdown
<!-- 悪い例: ラベルが文の言い換えになっている -->
- **検証**: 検証スクリプトで検証します。

<!-- 良い例: 名前の後に新しい情報が続く -->
- **prose-style.md。** AI 特有の言い回しの例と、その直し方があります。
```

## コード

### インラインコード

ファイル名、コマンド、フィールド名、引数は、バッククォートで囲みます。
`<file>` のように、そのまま書くとマークダウンとして解釈されてしまう文字列も、バッククォートで囲みます。

### コードブロックには言語を書く

複数行のコードは、字下げではなくフェンスで囲みます。
開始フェンスには言語を書きます。
言語があると、レンダラーが色を付け、Claude もコードの種類を取り違えません。
プログラムの出力やチェックリストのように言語がない場合は、`text` と書きます。

### 長いシェルコマンドは `\` で折り返す

長いシェルコマンドは、行末の `\` で折り返します。
`\` で折り返したコマンドは、そのままコピーしてシェルに貼り付けても動きます。

```bash
python scripts/fill_form.py \
    input.pdf fields.json output.pdf
```

### マークダウンの例は4つのバッククォートで囲む

コードブロックを含むマークダウンの例は、外側を4つのバッククォートで囲みます。
外側が3つだと、内側の3つのバッククォートで外側のブロックが閉じてしまいます。

## リンクの書き方

### リンクテキストには行き先の名前を書く

「こちら」「ここ」「link」や、URL そのものをリンクテキストにしません。
リンクだけを拾い読みする人や、スクリーンリーダーの利用者に、行き先が伝わらないからです。
まず文を書き、その文の中で行き先を表す語句をリンクにします。

```markdown
<!-- 悪い例 -->
詳細は[こちら](references/forms.md)を参照してください。

<!-- 良い例 -->
詳細は[フォーム入力ガイド](references/forms.md)を参照してください。
```

### パスは SKILL.md からの相対パスで書く

スキルの中のリンクは、SKILL.md があるディレクトリからの相対パスで書きます。
パスの区切りにはスラッシュを使います。
`../` は使いません。
Google のガイドは `../` を避けるよう勧めており、Anthropic のガイドは参照を1階層にするよう勧めています。

### 参照スタイルのリンク

URL が長くて文が読みにくくなる場合や、表の中にリンクを置く場合は、参照スタイルのリンクを使います。
リンク先の定義は、そのリンクを最初に使った節の末尾、次の見出しの直前に置きます。
複数の節で使う定義は、ファイルの末尾にまとめます。

```markdown
手順は [Agent Skills のベストプラクティス][best-practices] に従います。

[best-practices]: https://platform.claude.com/docs/ja/agents-and-tools/agent-skills/best-practices
```

本文の中にそのまま書いても読みやすい短いリンクには、参照スタイルを使いません。

## 画像

画像は、文で説明するより見せたほうが早く伝わる場合にだけ使います。
画像には代替テキストを書きます。
代替テキストがあれば、画像を見られない読み手や、テキストだけを読むツールにも内容が伝わります。

## 表

表は、次の条件をすべて満たすデータにだけ使います。

- 読み手が項目を素早く見比べる必要がある。
- データが行と列の2方向に均等に並ぶ。
- 同じ種類の項目が多く、項目ごとに異なる値を持つ。

空のセルが多い表、行数と列数の差が極端な表、セルに長い文が入る表は作りません。
そうしたデータは、リストか小見出しで書きます。

## HTML

HTML は使わず、マークダウンの記法で書きます。
HTML はソースのまま読みにくく、レンダラーによっては表示されません。

-   古い情報は `<details>` で折りたたまず、`## 古いパターン` という見出しの下に書きます。
-   改行のために `<br>` を使わず、段落を分けるかリストにします。
-   `<name>` のような山括弧のプレースホルダーは、バッククォートで囲みます。
    囲まないと、レンダラーが HTML のタグとして扱い、表示しないことがあります。

## スキル向けの調整

Google のガイドは、人が読むドキュメントサイトを前提にしています。
Anthropic のガイドは、Claude が読むスキルを前提にしています。
前提の違いから2つのガイドが食い違う箇所は、次のように扱います。

### 目次の扱い

Google のガイドは `[TOC]` を使うよう勧めています。
しかし `[TOC]` を目次として表示するのは Gitiles だけで、GitHub は表示しません。
Claude にとっても、`[TOC]` は意味のない文字列です。
そのため、見出しへのリンクを並べた `## 目次` を手で書きます。
この目次は、100行を超える参照ファイルに目次を置くという Anthropic のガイドの規則も満たします。

### 古い情報の置き場所

Anthropic のガイドの例は、古い手順を `<details>` で折りたたんでいます。
このスキルでは HTML を避けるため、古い手順を `## 古いパターン` という見出しの下に書きます。

### ワークフローのステップ

Anthropic のガイドの例は、各ステップを太字の行で書いています。
このスキルでは、各ステップを H3 の見出しにします。
見出しにすると、リンクで直接そのステップを開けて、アウトラインにも表示されます。
Claude がコピーして使うチェックリストは、`text` のコードブロックに書きます。
