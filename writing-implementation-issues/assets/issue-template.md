# TODO Issue のタイトル

## 目的

TODO 何のための変更か、利用者や開発者にとって何が変わるかを2〜3文で書きます。

## 完了条件

- [ ] TODO 確かめられる文で書きます。
    例: 登録済みのメールアドレスに招待を送ると、画面にエラーが出る。

## 作業ステップの一覧

- [ ] Step 1: TODO
- [ ] Step 2: TODO
- [ ] Step 3: TODO

## 用語の対応表

この Issue の文、図、コード例の名前は、すべて次の表に揃えています。

TODO 列は、リポジトリの規約で使う表記だけにします。見出しには表記の名前と、使う場所を書きます。

| 日本語 | camelCase | PascalCase | kebab-case |
| --- | --- | --- | --- |
| サンプルドキュメント | `sampleDocument` | `SampleDocument` | `sample-document` |

## 既存の規約

実装は次の規約に従います。
迷ったら、根拠のファイルを開いて書き方を合わせてください。

-   TODO 規約を1文で書き、根拠のファイルを添えます。
    例: ユースケースは1ファイル1関数で、`src/usecases/` に置く。
    根拠は `src/usecases/create-user.ts` です。
-   TODO エラーの扱い方。
-   TODO テストの置き場所と名前。

## 変更するファイル

```text
TODO ツリーを書きます。各ファイルの行末に [追加] [変更] [削除] と作業ステップの番号を書きます。
```

## 処理の図

TODO 図で答える問いを1文で書きます。
例: 管理者が招待を送るボタンを押すと、最終的に何が行われるか。

```mermaid
sequenceDiagram
    TODO 操作する人、システム、アクションの相手を参加者にします。
```

TODO 色の意味、行われるアクションの一覧、根拠のファイルを書きます。

## 作業ステップ

### Step 1: TODO

TODO この作業ステップの目的を1〜2文で書きます。

#### Step 1 で変更するファイル

- `TODO` [追加]

#### Step 1 のコード例

```ts
// TODO 追加するファイルのパス
TODO 主要な関数やクラスのシグネチャと、処理の大枠だけを書きます。import は書きません。
TODO 細部は `// ...` に続けて、そこで何をするかを1行で書いて省きます。20行程度までにします。
TODO フェンスの言語は、リポジトリの言語に合わせます。
```

```diff
// TODO 変更するファイルのパス
TODO 変更箇所を、前後の既存のコードを数行ずつ含めて書きます。
```

#### Step 1 のテストの観点

- [ ] TODO 観点と、入力と期待する結果を1行で書きます。

#### Step 1 でテストしないこと

- TODO テストしないことと、その理由を書きます。

#### Step 1 の完了条件

- [ ] ビルド、リンター、既存のテストが通る。
- [ ] TODO

### Step 2: TODO

TODO Step 1 と同じ形で書きます。

## 未決事項

-   TODO 実装の前に筆者が決める必要があることを書きます。
    ない場合は、この節を削除します。
